# 工作流 · 第 3 步：编译 Hook、Style 和 Play

> 本文件是第 3 步的权威正文。进入本步时即时读取。

## 3. 编译 Hook、Style 和 Play

只要存在任何 GUI 或文本形式的 Hook、创意/Play、Style，就读[创意与分镜](../base/creative-and-storyboard.md)并生成一份内部 `融合创意规格`（该文件约 548 行，按「全局文件读取设置」读到末尾再动手）。**本步编译 Hook/Play/Style 的权威规则（「Hook 脚本合同」「模板商品化适配合同」「可投放商用脚本合同」）在根级 `contract-creative-and-script.md` 里，进入本步前必须对 `contract-creative-and-script.md` 过 SKILL.md 不变量 #14「真读门」，否则不得编译 Hook。** **禁止把用户 Prompt、Hook Prompt、Play Prompt、Style Prompt 依次拼接或各分配一段时间。**它们必须共同作用于同一条商品因果链。

先建立唯一事实底座：`用户目标与锁定文案 + 商品模型 + 卖点账本 + 图片可见特征 + 主证明 + 时长/平台/安全限制`。图片只授权可见的形、色、材质、结构和文字，不授权推断隐藏结构、真实用法或功效。随后为每个所选模板拆出：

- `机制不变量`：用户选择后必须保留的注意力原理、叙事玩法或视听语法；
- `表层变量`：示例中的地点、人物、道具、动作、镜头顺序、颜色和措辞，默认按商品重写；
- `商品绑定`：该机制具体绑定哪条受众压力、卖点、使用动作或证明；
- `可观察落点`：它会改变哪个镜头、动作、声音、构图、剪辑或状态变化；
- `成功标准`：移除该模板后，成片必须出现可观察差异。

按角色联合编译：Hook 负责在第一拍提出与商品有关的问题、反差、结果或信息缺口；创意/Play 负责从第一拍开始组织叙事、动作与证明路径；Style 作为全片统一的视听生产语法。**Hook 的最后一个动作必须同时是 Play/证明链的第一个动作**，bridge 是这一个动作的延续或解释，不是另加一段过场。默认不让人物首帧举商品口播，除非商品揭示本身就是所选 Hook 的机制。

随后完成 `adaptive_fusion`：先写当前 SKU 的 `product_specific_tension / opening_state / product_causal_action / proof_state / end_state`，再分别写每个已选 Hook、Play、Style 对具体镜头造成的 `module_observable_effects`。若人物承担 Hook、叙事、口播或体验职责，再写 `human_performance`，把心理状态翻译成触发源、可观察行为、行动意图、环境作用、发声方式和结果反应；不得只写“生气、嫌弃、认真、释然、自信微笑”等情绪标签。若无人脸或纯商品，则用物体、环境和任务状态完成同一条状态链，不为过检查强加人物。

先定主证明，生成至少三个内容程序候选，自动淘汰 SKU/素材/Hook 闭环/时长/平台执行不合格者，再从合格候选找能自然提出主证明问题的 Hook。不授权未核实功效。

选中候选后必须写清内部 `hook_question / product_action / proof_answer_shot`。主证明镜头必须使用当前同一 SKU 完成 Hook 所承诺的同一任务；商品形态、功能部位、使用方式、作用目标或素材证据任一不支持，就判 0 分重选，不能换成邻近任务蒙混过关。若 Hook 使用奇观、强环境力或超现实空间，还须写 `spectacle_causality`：奇观怎样作用到人物/物体/任务、造成什么商品相关状态、怎样触发行动并交接主证明；只有背景替换而主体状态不变，直接判为奇观摆拍。启用抖音/TikTok 时，再按平台执行底线的八项原生感标准自动评分；任一项为 0 或低于阈值，重写首屏、镜头密度、人物观看关系、动作声与收尾，不请用户做普通质量筛选。

把以上决定整理为内部 JSON，并在进入第 4 步前运行 `python3 scripts/validate_creative_contract.py <contract.json>`。校验至少包含当前 SKU 形态、Hook 主张、证明回答镜头、`adaptive_fusion`、必要时的 `human_performance / spectacle_causality`、平台、时长、短视频执行指标及本地化状态。**该校验器所需 JSON 的完整字段模版见 [contract-json-schemas.md](../contract-json-schemas.md) 第 1 节;返回的 `errors` 已是中文自然语言,直接说清哪里出错、怎么改,照着改产物即可(能否读校验器源码等规则统一见该文件抬头)。** 返回非零或 `ok: false` 时按错误信息自动重选/重写并重新校验,不得忽略结果,也不得把普通纠错交给用户。临时 JSON 只用于校验，不作为交付产物。

场景按 `information_job` 编排：20 秒及以内优先一个主世界。`A→B→C→D` 只有在多使用情境、多人群、旅程、换装或蒙太奇确实是 Play 机制时才成立，且 A/B/C/D 每一场必须新增不同且必要的购买理由、证明或信息职责，共享同一 USP、商品识别和连续动作/声音/构图线索。重复职责的换景必须合并。离开某场景后默认永不重开：`A→B→A`、`A→B→C→A`、`A→B→A→B` 都是阻塞项。Hook 世界 A 交接到证明世界 B 后，在 B 完成结果和 CTA；只有用户明确锁定首尾回环才允许一次例外，Agent 不得自行以“因果兑现”放行。

冲突按 `事实与安全 > 用户明确硬约束/锁定文案 > 主证明可成立性 > 所选模板机制不变量 > 图片启发 > 示例皮肤/UI 默认` 裁决。先做**等价改写**：改地点、道具、表演、镜头或语气以同时保住机制，不得静默删除任一所选模板。只有机制之间在同一时长内确实互斥、等价改写仍无法兼容时，才向用户提出一个最小问题。

进入第 4 步前对 `融合创意规格` 做 8 项阻塞检查，每项 0–2 分：Hook 机制保真、商品专属性、Hook→Play 桥接、主证明有效、Play 落地、Style 全片一致、场景连续、动态状态因果。任一项为 0 或总分低于 13/16，先重写，不生成故事脚本。
