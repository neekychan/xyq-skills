# 创意类技能的黄金架构（八支柱 + 可抄范式）

当你创建**视频 / 图片 / 广告 / 品牌片 / 短剧电商 / UGC** 等创作类技能时，用本文件作为蓝本。它把三个标杆创意技能（品牌片、短剧电商、UGC 营销）共有的成功模式，抽象成可复用的八个支柱，并给出可直接套用的写法。

## ⚠️ 两条贯穿全文的硬规则（先读）

### 硬规则 A：产出语言必须跟随该技能的目标市场 / 受众
本文件给出的范式标题与样例句**默认用中文书写**。但产出的技能其 SKILL.md 与 references **必须使用该技能自己的工作语言**——与它的 `description`、目标市场、目标受众一致。
- 目标是中国大陆 / 抖音 / 中文语境 → 全文中文。
- 目标是 US / TikTok / 英语受众 → 全文英文。
- 多市场 → 主体用主市场语言，本地化执行部分用各自语言。

**严禁把本文件的样例句逐字照抄进产物**（无论中文还是英文样例）。它们只是结构示意，必须翻译/改写成目标语言。产出后自检：SKILL.md 里不应出现与目标市场不符的语言混杂。

### 硬规则 B：建造期元规则只"照做"，绝不"照抄进产物"
以下内容是**你（技能作者）在建造时要遵守的元规则**，它们**绝不能作为章节或说明文字出现在产出的技能里**：
- 「保密红线」——作者要做到"产物不点名内部工具"，但**不要把"保密红线"这一段写进产物**。
- 「会话隔离 / 构建期 / 母库 / mother library」——这是 skill-creator 的内部建造概念，写进产物等于把内部机制泄漏给最终用户，**本身就违反保密红线**。
- 「不打包脚本 / 建造约束」之类的建造说明——对最终用户无意义，不要写进产物。

注意：`tools` 字段是产物 frontmatter 的**正常必填字段**，不属于建造期元信息——它声明该技能依赖的生成工具，必须保留并填对（见 SKILL.md「`tools` 字段规则」）。

产出的技能只应包含**对完成创作任务有用的内容**（核心原则、诊断、路由、强制加载、工作流、输出契约、自检）。把任何"关于如何建造这个技能"的话留在 skill-creator 这边。

## 目录

1. 总纲：SKILL.md 是"路由中枢"，不是"执行手册"
2. 八支柱逐条范式
3. 一页式骨架（可整体复制到新技能 SKILL.md）
4. 为新技能撰写领域用词的方法
5. 常见反模式

## 1. 总纲：SKILL.md 是"路由中枢"

标杆技能的 SKILL.md 只承担**核心推理 + 路由**，所有可执行的工艺细节下沉到 `references/`。一句应当写进新技能的硬规则：

> 不要仅凭 SKILL.md 回答具体的创作任务；先按路由表读取相关 references，再生产。

好处：SKILL.md 保持精简（< 500 行），上下文按需加载，质量靠 references 的专业度兜底。

## 2. 八支柱逐条范式

> 下列模板标题/样例句均为中文示意。产出英文受众技能时，请整体译为英文（见硬规则 A）。

### 支柱 1：核心原则 + 持久引擎（因果链）

用一条**不变的因果链**表达该领域的思维模型，作为整个技能的脊柱。

写法模板：
```markdown
## 核心原则

<一句立场，常以"不要只做 X，而要做 Y"表达，点出该领域最常见的失败。>

持久引擎（因果链）：

**A -> B -> C -> D -> ... -> 最终交付物**
```
范例（按领域替换链条）：
- 品牌片：`市场 -> 品类张力 -> 受众压力 -> 文化时机 -> 品牌资产 -> 片种 -> 视觉创意 -> 产品角色 -> 证据 -> 本地化品牌语`
- 短剧电商：`产品品类 -> 目标受众 -> 短剧类型 -> 受众幻想 -> 关系压力 -> 3 秒异常钩子 -> 升级冲突 -> 产品作为剧情功能 -> 可见证据 -> 情感回报 -> 转化语`
- UGC：`产品信息 -> 痛点/卖点 -> 受众 -> hook -> 可见证据 -> 创作者真实感 -> 下一步行动（CTA）`

### 支柱 2：可证伪的质量测试

一句能判定"好/不好"的硬标准，逼迫创意必须让产品**结构性地不可替代**。

写法模板：
```markdown
### 质量测试（可证伪）

创意只有通过这条测试才算成立：

**没有这个产品，<主角/画面>就无法以这种方式 <取胜 / 和解 / 揭真相 / 完成任务 / 触发转折>。**
```
追加"产品角色清单"帮助落地（关系加速器、身份线索、救援工具、转化证明、地位信号、任务道具、最终揭示钥匙……）。

### 支柱 3：富输入诊断（Input Diagnosis）

列出生产前必须明确或合理假设的维度。标杆通常 10–20 项。

写法模板：
```markdown
## 输入诊断

生产前，识别或合理假设以下维度：

- 目标市场 / 语种：
- 品类与主要购买场景：
- 目标受众（越窄越好）：
- 品类张力 / 痛点：
- 产品真相（产品能让人看见的最小具体能力）：
- 证据标准（受众需要看到什么才相信）：
- 片种 / 体裁：
- 表现形式（实拍 / CGI / 动画 / 混合媒介）：
- 风格参照（翻译成镜头/光/色/节奏/声音，而非直接点名一部片）：
- 合规敏感点：
（按领域增删）

若用户给的上下文很少，做合理假设并继续。仅当产品、市场或目标确实无法推断时才发问。
```

### 支柱 4：路由表（Routing Table）

按 品类 / 格式 / 市场 / 平台 把任务路由到对应 reference，并要求"**只读匹配项**"。

写法模板：
```markdown
## 路由表

针对具体任务，只读取匹配的 references：

- 品类为美妆/个护 -> `references/industries/beauty.md`
- 品类为食品饮料 -> `references/industries/food-beverage.md`
- 目标平台为 TikTok/Reels/Shorts -> `references/formats/platforms.md`
- 写最终视频 prompt -> `references/formats/video-prompt.md`
- （可选）使用 CGI/VFX 且已建 craft/ -> `references/craft/vfx.md`

craft 层默认不建；仅当它是任务核心（或用户/上传文件已提供）时才单独成文并在此登记。
静默使用 references；除非用户问起，否则不提及。
```

### 支柱 5：强制参考加载契约（带 hard rule）

把"必读 + 条件读取 + 一条 hard rule"写死，作为质量下限**机制**。

写法模板：
```markdown
## 强制加载 reference

写任何最终产出前，先读取任务所需的 references（以能力方式读取下列相对路径文件）。

必读：
1. `references/formats/output-spec.md`
2. `references/<核心工艺>.md`

条件读取：
- 涉及具体产品品类时读 `references/industries/<品类>.md`。
- 平台影响格式/节奏/CTA 时读 `references/formats/platforms.md`。

硬规则：若最终答案包含 `video_generation_prompt`，则本回合必须已读过写 prompt 的那个 reference。
```

### 支柱 6：输出契约（Output Contract）

固定字段 spec 模板 / 带时间戳的分镜 beat 结构，保证可直接粘贴使用。

写法模板（视频）：
```markdown
## 输出契约

默认产出：

Rationale（创意逻辑）：<1-3 句解释 hook / 证据 / 转化逻辑>

video_generation_prompt:
0-3s: <相机> <画面> <品牌/产品曝光，可见时> <声音> <一句口播>
3-7s: ...
7-12s: ...
12-15s: ...
```
要求：每个 beat 以`相机`起手，依次`画面 / 品牌-产品曝光 / 声音`；用稳定标签 `Brand1 / Product1 / Subject1 / Scene1` 绑定复现实体；正向措辞，不写否定式约束（否定式留在内部自检）。

> ⏱️ **在输出契约里写清 15s 一次成片规则。** 产出技能若涉及短视频，务必在其输出契约/工作流里说明：**时长 ≤15s 的视频用一次视频生成即可拿到完整成片**——上面的 0-3s/3-7s/7-12s/12-15s 是**同一条 prompt 内的时间轴**，不是分段多次生成；只有成片 >15s 时才拆成若干 ≤15s 片段分别生成再后处理拼接。以能力方式表述（"一次生成一段 ≤15s 的成片"），不点名内部工具。

### 支柱 7：静默自检（Silent Self-Check）

交付前内部跑清单并**重写弱项**，不暴露给用户。

写法模板：
```markdown
## 静默自检

开发期执行；定稿前重写弱项。
除非用户要求点评，否则不要把这份清单输出给用户。

- 因果链是否每一环都成立？
- 质量测试是否通过（产品是否结构性不可替代）？
- 前 3 秒是否有钩子且与首个画面动作一致？
- 成片时长是否 ≤15s？若是，是否作为一次生成的完整片段（多段 beat 写在同一条 prompt 内），而非分段拼接？若 >15s，是否已切成 ≤15s 片段分别生成再拼接？
- 灯光/运镜/声音是否具体到可生成？
- 结尾是否形成品牌记忆点（产品可见 + logo 可读 + 品牌语 + 声音线索）？
- 文化/合规/夸大/披露风险是否处理？
- 全文语言是否与目标市场一致、无混杂？
```

### 支柱 8：领域用词库与工艺清单（references/）

把灯光、运镜、VFX、声音、hook 句式、品类策略、市场文化与合规等**专业用词**沉淀为参考文件。按该技能领域直接撰写（见第 4 节）。

## 3. 一页式骨架（可整体复制到新技能 SKILL.md）

> 下列骨架为中文示意。若目标受众为非中文市场，请整体译为目标语言（硬规则 A）。
> 注意：骨架里**不含**"保密红线 / 会话隔离说明"等建造期元信息（硬规则 B）；但 frontmatter 的 `display_name`（中文展示名）与 `tools` 字段是必填的正常字段，必须保留并填对。

```markdown
---
name: <hyphen-case-name>
display_name: <中文展示名，给最终用户看，必须为中文，例如 倒挂金钩；尽量 ≤10 个中文字符>
description: <做什么 + 何时用；含触发场景、格式、目标市场；≤1024 字符；不含尖括号>
tools: <生成工具白名单：只生图 ["sandbox_generate_image"]；只生视频 ["render_video", "sandbox_generate_video", "sandbox_process_video"]；两者皆有则四个全列>
# 以下两行为可选字段，默认**不写**；仅当用户显式要求指定模型、或从用户输入/上传内容里识别到模型信息时才加，取值见 model-catalog.md
# image_model: <支持清单中的图片模型取值>
# video_model: <支持清单中的视频模型取值>
---

# <Title>

## 核心原则
<立场一句 + 持久引擎因果链 + 可证伪质量测试>

## 输入诊断
<10-20 个生产前维度（含目标市场/语种）>

## 路由表
<按品类/格式/市场/平台路由到 references/，只读匹配项>

## 强制加载 reference
<必读 + 条件读取 + 一条 hard rule>

## 工作流（步骤）
<分步骤 SOP：解析输入 -> 诊断 -> 路由读参考 -> 选策略 -> 生产 -> 自检 -> 交付>

## 输出契约
<固定字段 spec / 带时间戳 beat 模板>

## 静默自检
<交付前静默自检清单>
```

> 路径写法：正文一律用相对路径 `references/...`，并以能力方式描述读取动作（"读取本技能下的 `references/xxx.md`"），**不点名任何内部工具**。

## 4. 为新技能撰写领域用词的方法

产出的技能在用户侧运行时是**隔离的，只能读到它自己 `references/` 里的内容**。因此必须把领域专业用词按该技能领域直接写进新技能自己的 `references/`：

1. 按访谈结论确定：领域（行业）、格式/体裁、目标市场/平台/语种；**工艺层(craft)按需，非必填**；**生成模型默认不设置**（仅用户主动点名时才写 frontmatter 的模型字段）。
2. 据此列出该技能需要的 `industries/` + `formats/` 词条清单；`craft/` 仅在工艺是核心、用户要求、或上传文件已含工艺信息时才列入。
3. **贴合领域撰写**：把"模式 + 句式样例"写成贴合该技能领域**且语言一致**的版本，只保留相关品类，补上该技能特有的产品角色与合规点。
4. 写进新技能的 `references/`（默认 `industries/ formats/` 两类；需要时再加 `craft/`），并在 SKILL.md 的路由表 + 强制加载契约里登记它们。
5. 在每个用词库文件顶部写一句："这些是**可适配的模式与句式**，按场景改写，不要逐字照搬。"——防止产出千篇一律。

> ⚠️ **不要默认铺 `craft/`。** 空写工艺层会明显拖慢生成且产出稀薄。默认不建 craft，把必要工艺要点内联进 `formats/` 的 prompt 文法或输出契约即可；只有用户明确要求或上传文件已含工艺信息时，才单独建 `craft/`。

> 注意（硬规则 B）：产出技能的 references 里只保留领域词条本身，**不要写"因会话隔离…"之类的建造期说明文字**。

## 5. 常见反模式

- **SKILL.md 自带全部细节** → 该下沉到 references。
- **没有质量测试** → 创意失去"产品不可替代"的硬约束，产出平庸。
- **参考加载只是软建议** → 缺质量下限；必须有 hard rule。
- **输入诊断只有一句话** → 产出不会"先诊断后生产"。
- **用词库逐字照搬** → 千篇一律；要标注"可适配，按场景改写"。
- **prompt 用否定式堆砌** → 视频模型对正向执行措辞更友好；否定式留在内部自检。
- **结尾只有静默 logo 卡** → 缺品牌记忆点（应含产品可见 + 可读 logo + 品牌语 + 声音线索）。
- **语言混杂**（违反硬规则 A）→ 产物语言与目标市场不符，或中英文样例直接照抄未翻译。
- **泄漏建造期元信息**（违反硬规则 B）→ 产物里出现"保密红线 / 母库 / 会话隔离 / 构建期"等章节或说明，把内部建造机制暴露给用户。
- **`tools` 字段缺失或填错** → 产物 frontmatter 没声明 `tools`，或视频技能只列了三件套的一部分，或混入白名单外的工具名 → 校验失败。
- **`display_name` 缺失或非中文** → 产物 frontmatter 没声明 `display_name`，或填了英文/拼音 → 校验失败（必须为中文展示名，例如 倒挂金钩）。
- **擅自设置模型字段** → 用户根本没提模型，却自作主张写了 `image_model` / `video_model`，把技能锁死在某个模型上 → 默认应不写这两个字段，交由平台默认模型执行。
- **模型取值填错** → 写了展示名（如 `Seedream 5.0 Lite`）而非取值、自造版本号、或与 `tools` 不自洽（写了视频模型却没列视频三件套）→ 校验失败。取值逐字见 `model-catalog.md`。
