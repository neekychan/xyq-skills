# 电影感色卡 Skill

本 Skill 负责**色卡的生成、提取与确认**，并约定后续创作如何引用色卡保持色系一致。

本 Skill 的参考文件路径：`/workspace/.skills/palette_card/references/`

```text
references/
├── palette-usage.md          # 色卡 → 创作转写规范：参考图句式、色名词库、固有色保护（确认色卡后必读）
├── palette-play.md           # 玩法库：盲盒抽卡、色卡叙事、色卡巡游等（确认后、进垂类前必读一次）
└── scripts/
    ├── palette_card.py       # 色卡生成脚本（随机 / 视频提取 / 多图提取）
    └── pippit-logo.png       # 分享卡右下角 logo（脚本自动读取）
```

## 一、任务边界（重要）

**本 Skill 只做两件事：生成/提取色卡 → 用户确认交付。**

1. **不负责任何视频制作**。用户确认色卡后要继续做图/做视频，必须 `load_skill` 对应创作 skill 再走其完整流程；色卡只作为贯穿性的色彩约束叠加在创作流程之上。**创作类 skill 不一定已注入本会话**——以 `<available_skills>` 实际列表为准，只加载列表里存在的 skill，不要凭猜测点名。

2. **色卡是追加约束，不是流程简化**：进入垂类后其全部流程门（创意设计、各阶段确认门、自审清单、ref 加载顺序）一律照常执行，不得因"色卡已确认过一次"而省略垂类自身的确认门。**交付终止权归垂类 skill**：垂类 `present(成片, interrupt=true)` 是全流程最后一个动作，本 skill 不得在其后追加任何动作或"要不要做更长版本"之类延展建议——但 §五 的收口分享卡与固定文案属于成片交付的一部分，必须**排在垂类 present 之前**完成，不属于延展建议。**成片交付后的每个后续轮**，若用户只回纯确认/催促语（"确认""好的""按你推荐继续""继续"），唯一动作是一句话复述已交付成片路径并等待；禁止列举"加长版/换色卡/换题材"等方向清单、禁止发问卷、禁止 `load_skill`、禁止再次生成。

3. **工具缺失即停（红线）**：
   - **判定方式唯一**：看当前工具面里有没有 `sandbox_generate_image` / `sandbox_generate_video` 这两个工具名。禁止用 `sandbox_bash` 做**任何形式的能力/工具/skill 存在性探测**——包括但不限于 `which`、`pip list`、`ls`（含 `ls /workspace/.skills/`）、`echo`、空命令。工具面与 skill 可用性只看两处：当前工具面里的工具名、`load_skill` 的返回值；`load_skill` 返回 not found 即是结论本身，不得再用 shell 列目录二次确认。判定一次即成立，跨轮沿用结论，不得重判。
   - **停机动作**：`present_sandbox_file(选定分享卡, interrupt=false)` 展示色卡，一句话说明本会话无生成工具、色卡已交付，并询问用户下一步想做什么（出路提示见下条），随后结束本轮等待回复。停机结论跨轮沿用，后续轮不得再推进制作。
   - **不许代写方案**：`load_skill` 垂类返回 not found / inaccessible 时，**该轮立即执行上面停机动作后终止，禁止任何其它工具调用**（含 todo_write / mkdir / 写 Prompt / 写方案文本），并一句话告知用户：本会话没有对应创作 skill，色卡已交付，**可换用会话内其它已有 skill，或另起一个具备该能力的会话引用这张色卡**（出路提示不可省略）。停机后的后续轮同样不得输出创作方向、片名、场景描述、分镜、生视频 Prompt 等具体创意内容——即使用户回复"按你推荐继续"，正确动作仍是复述已交付内容并等待。没有垂类红线背书的分镜/Prompt 交付出去反而误导用户。
   - **禁止结果而非仅禁止手段**：工具不可用时，禁止用任何代码手段（PIL 绘图、ffmpeg zoompan/合成、numpy 生成音频、伪造输出路径等）产出任何看起来像生成结果的 `.png`/`.mp4`/`.wav`——**写出这类代码即违规，不论是否落盘、不论是否声明为"占位/验证/演示"**。本 skill 唯一允许执行的绘图代码是 `palette_card.py` 本身。
   - **`sandbox_bash` 白名单（只此两类，其余一律非法）**：① `mkdir` 建目录；② 运行 `palette_card.py`（含 ffmpeg 抽帧供创意判断）。任何其它用途——`echo`、`python3 -c`、`ls`、写 `.py`/`.json` 再回读执行、探测工具/skill、校验生成产物——全部非法，不接受任何"检查一下""准备一下"的理由（脚本 stdout 已印产物路径，无需 ls 确认）。
   - **"已生成/已产出"话术口径**：下方"禁止话术"只针对 `sandbox_generate_*` / `render_video` 生成工具；描述 `palette_card.py` 的脚本产出（色卡）说"已产出/已渲染"是合法的。
   - **禁止中间任务文件（扩展判据）**：生成参数（prompt / images / output / ratio / duration 任一）出现在 bash 命令体或落盘文件里即违规，不论是否包含工具名字符串——生成参数只能出现在真实的生成工具调用参数里，现写现传。
   - **禁止空头 todo（含时序）**：依赖 `sandbox_generate_image` / `sandbox_generate_video` / `render_video` 的 todo 条目，只允许出现在 `load_skill` 成功加载带生成工具的创作 skill 之后；工具面无生成工具时出现即违规。todo 对用户可见，写下不可能完成的条目等同于"正在生成"话术。
   - **禁止话术**：未真正调用生成工具时，不得使用"正在生成""并行生成中""已生成"等措辞。**问卷选项文案同样受此约束**——停机后不得再发任何含玩法/场景/分段时长描述的问卷，选项 description 里写场景等同于输出方案。
   - **停机后复述只用自然语言**给出色卡标题与文件路径，禁止再次 `present` 同一张分享卡（重复推送是对用户的轰炸）。
   - **唯一合法产物**：色卡分享卡 + 一句自然语言说明。

4. 色卡确认后，本会话内**所有** `sandbox_generate_image` / `sandbox_generate_video` 调用（含角色参考图、场景资产、故事板、正片各段）都必须按 `references/palette-usage.md` 执行三步转写——这是叠加在任何垂类 skill 之上的全局规则。

5. **生成工具返回产物即视为成功**：`sandbox_generate_image` / `sandbox_generate_video` / `render_video` 返回产物路径后，禁止再用 `ffprobe` / `ls` / `cat` 校验文件大小或时长，禁止因"校验失败"而 sleep 等待或重复生成同一段 Prompt。需要确认元信息时只用 `sandbox_read`（返回尺寸/时长/caption）。重复生成会给用户推送多份中间产物。

## 二、模式路由

| 用户信号 | 模式 | 做法 |
|---------|------|------|
| 「随便给我个色卡」「来点配色灵感」「抽一张色卡」 | **A 随机色卡** | 先读 `references/palette-play.md`（随机抽卡本身就是玩法 A，禁止用 `omni_search` 热点复刻替代玩法库），再用脚本 `--random` 生成 2~3 张候选让用户挑 |
| 上传了视频/多张截图 +「提取色卡」「总结这组图的色系」 | **B 提取色卡** | 脚本以上传素材为输入提取 |
| 用户直接给出色值/色名/成品色卡图 | **C 直接确认** | 跳过生成，径直进入确认交付 |
| 只说「做视频时颜色要统一」没给素材 | 先问 | 问卷确认走 A 还是 B（有无参考素材） |

**问卷边界**：`dynamic_questionnaire` 在本 skill 内**只用于三件事**——素材缺失时确认走 A 还是 B、模式 A 多张候选让用户选卡、步骤 4 玩法二选一。**单张色卡（模式 B/C）不发确认问卷**——`present(interrupt=true)` 已经把决定权交回用户，再发"是否满意"单题表单是多余的点击成本。禁止用问卷询问视频题材/风格/时长等创作维度，这些属垂类职责，未加载垂类前不得代问。

## 三、执行流程

### 步骤 1：生成色卡

脚本路径：`/workspace/.skills/palette_card/references/scripts/palette_card.py`

```bash
# 模式 A：随机（并行生成 2~3 张候选；seed 用 shell 的 $RANDOM 取，禁止自己编数字——
# 模型挑数字有偏好，会让"随机"色卡趋同）
python3 /workspace/.skills/palette_card/references/scripts/palette_card.py --random $RANDOM -o output/palette/card_1.png

# 模式 B：一个视频 或 多张截图
python3 /workspace/.skills/palette_card/references/scripts/palette_card.py 用户素材.mp4 -o output/palette/card.png
python3 /workspace/.skills/palette_card/references/scripts/palette_card.py a.jpg b.jpg c.jpg -o output/palette/card.png
```

- 脚本产物即 `card_*.png` 色卡图，落 `-o` 指定的项目目录：既用于 present 给用户，也直接作为后续生成的色彩参考图。示例中 `output/palette/` 仅为示例路径，实际按本次项目目录落盘。
- **依赖先跑后补**：直接跑脚本，仅当报 `ModuleNotFoundError` 时再 `pip3 install --break-system-packages numpy pillow`（PEP668 环境下 `--user` 会被拒）。
- **ffmpeg 兜底**（模式 B 视频输入）：报 `ffprobe/ffmpeg not found` 或 `decoded zero frames` 时→不重试、不自行安装、不改用其它方式猜色；改请用户上传 3~5 张代表性截图走多图提取；无法提供则说明后停在此处。
- **产物一旦生成即固定**：脚本 stdout 的 `wrote <路径>` 行即产物凭证，无需 `ls` 二次确认；禁止为"确认存在"而重跑脚本（仅在用户要求换 `--colors` / `--merge` 重提时重跑）。
- stdout 每色一行：`hex 占比 H/L/S 色相族 可选色名:...`，外加**诗意标题（`title:` 开头那行）**——H/L/S、色相族、可选色名都是脚本实测值，**色名只能从该行"可选色名"里挑，禁止自行估算色相或从记忆里取词**（贴边色相不豁免，以 stdout 为准）。
- 需要看原片内容做创意判断时，用 ffmpeg 抽 2~3 帧到项目目录下再 `sandbox_read`——`sandbox_read` 只能读 `/workspace` 下路径，勿用 `/tmp`。

`card_*.png` 一图两用：present 给用户展示，同时就是后续生成的色彩参考图（转写句式见 `palette-usage.md`）。

### 步骤 2：展示并确认

**硬前置**：present 分享卡之前必须先 `sandbox_read` `references/palette-usage.md`（重点 §三固有色保护 + §四色名词库）——未读词库就写解读视为违规；发选卡问卷那一刻词库必须已在上下文中。

先输出**配色表**（产物锚点；**行数 = 卡面色格数 = 6，stdout 第 7 行及以后不进表**）：

```markdown
| hex | H/L/S（抄 stdout） | 色相族（抄 stdout） | 词库色名（中/英） | 占比 |
|-----|---------------------|--------------------|------------------|------|
| #938F85 | H45 L55 S06 | 中性 | 暖米灰 warm taupe | 24.0% |
| ...（卡面 6 色逐行） |
```

再基于该表用 `present_sandbox_file(interrupt=false)` 逐张展示分享卡（过程展示，不中断）。每张配一句四要素解读：**《标题》＋一句气质解读＋主色/辅色色名（抄配色表）＋适合什么片**。色名规则只有一条：**从该色 stdout 行的"可选色名"列表里挑一个**（可加"深/浅/柔"等明度前缀，近黑/近白行禁叠前缀）——不估色相、不从记忆里取词、贴边不豁免。气质解读里的意象词不得与色名混写——色名只出现在配色表与主/辅色字段。**色名只用于展示与收口文案，不进生成 Prompt**（生成 Prompt 只写 §四的一句定义句）；此处定死后收口文案沿用同一套词，不得改口。

**（若已知创作主体）固有色豁免需用户决策时**：主体固有色按 `palette-usage.md` §三判据（色相族集合 + 饱和度/占比下限）不在色板时，需要一道 A/B 单选（A 换含主体色相的色卡 / B 保留固有色只锁环境色·推荐）——模式 A 合并进选卡问卷，不另起；模式 B/C 本无问卷，此时才允许发一次仅含这道单选的问卷（这是单张色卡唯一发问卷的情形）。不得在推理文本里单方面决定。

然后确认：
- 模式 A（多张候选）：问卷让用户选卡（附"都不满意，再抽一组"选项）；
- 模式 B/C（单张结果）：**不发问卷**——直接进入步骤 3 交付，配一句话说明"不满意可以让我重新提取，可调整颜色数量/合并程度"，用户自然语言回复即可；不符合预期时调 `--colors` / `--merge` 重提。

跳过确认的判据从严：仅当用户明确表达**对这张色卡本身**的认可（如"就用这个色卡""这个配色可以"）才跳过；"直接帮我做视频"这类只表达创作意愿的话**不算**对提取结果的确认，仍须走确认。

### 步骤 3：交付

色卡确认后即交付：`present_sandbox_file(filepath=选定分享卡, interrupt=false)` 展示最终色卡，然后**一句话询问用户下一步想做什么**（可以用这张色卡做图或做视频），结束本轮等待回复。**交付不用 `interrupt=true`**——色卡不是会话终点，中断推送会把对话收死；`interrupt=true` 只留给垂类成片交付（§五）。

把下一步交回用户决定：本轮到询问为止，**禁止在同一轮内自行选定题材、搜热点、写剧本或加载垂类 skill**——即使用户初始输入带了"想找灵感""想做视频"这类模糊词；询问后不得再有任何工具调用。后续生成的色彩参考图就是选定的 `card_*.png` 本身（用实际生成路径，不得硬编码）。

**例外（授权只到 load_skill 为止）**：用户初始输入已明确给出视频题材与要求（如"抽张色卡然后做橘猫散步视频"）时，视为已授权**跳过本步的交付询问**（不必先问一轮"下一步做什么"）——但该授权**只允许你去 `load_skill` 匹配的创作 skill，不允许你直接开始制作**：`load_skill` 未成功返回前，写任何角色设定/分镜/生图生视频 Prompt 一律非法；`<available_skills>` 列表无匹配或 `load_skill` 失败 → 立即走 §一.3 停机动作。授权也不豁免垂类 skill 自身的任何确认门/问卷/硬停（以该垂类 SKILL.md 实际定义为准）。

**反例锚点（以下是真实违规样本，出现同款行为即违规）**：
- ❌ `sandbox_bash: ls /workspace/.skills/`（探测 skill 列表——skill 可用性只看 `<available_skills>` 与 load_skill 返回值）
- ❌ `sandbox_bash: echo '{"tool":"sandbox_generate_image",...}' > tasks/scene.json`（工具名字符串进 bash 命令 = 伪造/中转）
- ❌ 未 load_skill 成功就写"角色设定：橘猫，圆脸…镜头1：…"（自我授权接管制作）

### 步骤 4（下一轮或已授权时）：引导后续创作

1. 读取 `references/palette-usage.md` 与 `references/palette-play.md`；告知色卡已确认为本次会话的色彩基调；
2. 说明接下来可以**用这张色卡做图或做视频**（不点名具体品类——创作类 skill 未必已注入本会话，能否接走以 `<available_skills>` 实际列表为准；列表里有匹配的创作 skill 才能继续制作）；提议玩法时给最多 2 个候选——每个候选以 `palette-play.md` 的四行格式写进回复正文，`dynamic_questionnaire` 的 option 仅作选择入口，**不得用 option description 替代四行**；提议轮以玩法选择问卷收尾（问卷会等待用户提交），不再重复 present 分享卡；

4. **移交垂类前把已确认信息一次性写清**（色卡、玩法、方向、素材有无）。本会话无上传素材时，在垂类的角色来源问卷里预先替用户注明推荐"帮我生成角色形象"并说明理由，但该问卷仍须照发（人设选填题不得省略）。


## 四、色卡引用强制规则（色卡确认后全程生效）

完整句式与示例见 `references/palette-usage.md`。三条是**不可拆的原子动作**：ImageList 出现色卡 ⇒ Prompt 必须同时出现色系定义句与防入画尾注，三者缺一即该次调用非法，必须重写后再发。**中间参考素材生图（角色图/场景图/故事板）同样适用，无豁免。**

1. **参考图必带**：每次生图/生视频的 `ImageList` 都加入选定的 `card_*.png` 色卡图（与角色/场景参考图并存，色卡放列表末位）。
2. **定义句必写**：`将@图片N定义为全片色彩基调，全程统一色彩风格与调色，避免帧间色彩闪烁。`（`@图片N` 引用，句首禁加"参考"二字；**只此一句，不追加色名/hex 叙述**——色彩由色卡传递。参考图生图用"整体色彩基调"。）
3. **防入画尾注必加**：「@图片N 仅作为色彩参考，画面中不要出现色卡、色条、色块拼接图形及其上的文字」。

## 五、交付收口（强制，进入垂类制作时）

顺序错了就等于丢失收口——垂类 `present(成片, interrupt=true)` 后任何追加动作都会被其终止铁律拦掉，所以收口必须**前置**：

1. **片尾色卡入片**：`render_video` 拼接时直接把选定的 `card_*.png` 作为最后一个素材追加进 `video_paths`（定格约 1~1.5s）——`render_video` 原生支持图片素材，**禁止先用 ffmpeg/ffprobe 转码或量尺寸**；`sandbox_generate_video` / `render_video` 返回产物即成功，收口阶段不得对成片跑任何 ffprobe/ls 校验，需要尺寸/时长只用 `sandbox_read`。成片自带"这支片的配方"，作者感署名。
2. **收口文案与分享卡和成片同一批推送**：在垂类的 `present(成片, interrupt=true)` **之前**，先 `present_sandbox_file(card_*.png, interrupt=false)` 并输出固定文案「本片全程以《{色卡标题}》为色彩基调，主色{主色名}，辅色{辅色名}」；成片的 `interrupt=true` 是全流程最后一个动作。
